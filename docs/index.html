Schema-first Spring GraphQL and federation

Products owns catalog identity and descriptive fields. Pricing adds commercial fields. Both are ordinary synchronous Spring Boot applications backed by immutable Java collections.

Each service exposes its runtime Federation SDL. Rover composes those schemas into a supergraph, and Apollo Router serves the single client endpoint at http://localhost:4000/. No Apollo account or cloud service is required.

query {
  products {
    id
    name
    price
  }
}

The Router fetches products, constructs entity representations, asks Pricing for prices, and merges the response.

Entity identity with @key

interface CatalogItem @key(fields: "id") {
  id: ID!
  name: String!
  category: CatalogCategory!
}

The key allows an item to be recognized across subgraphs. Spring @EntityMapping turns Router representations into local Java values. Products uses a sealed hierarchy; Pricing uses a minimal reference object.

Entity interfaces and @interfaceObject

type CatalogItem @key(fields: "id") @interfaceObject {
  id: ID!
  category: CatalogCategory! @external
  price: Decimal!
  quote(input: QuoteInput!): Quote!
  priceLabel: String! @requires(fields: "category")
}

Pricing contributes fields once for every implementation of the Products-owned entity interface. The composed client graph still exposes the real interface and concrete types.

Polymorphism

query {
  catalog {
    id
    __typename
    ... on Product { weightGrams }
    ... on DigitalProduct { downloadFormat }
  }
}

A GraphQL type resolver maps the sealed Java implementations to Product and DigitalProduct. Tests assert exact subtype data and __typename values.

@external and @requires

Products owns category. Pricing marks it external and requires it to compute priceLabel. The Router transports the field even when the client did not request it, then omits it from the response. Tests prove the enum survives the complete federation representation round trip.

Enum, input object, and custom scalar

enum CatalogCategory {
  PHYSICAL
  DIGITAL
}

input QuoteInput {
  quantity: Int!
}

The enum supplies a closed domain and exhaustive Java mapping: PHYSICAL becomes “Physical price” and DIGITAL becomes “Digital price”. The input object groups quote arguments and binds to a Java record.

product(id: "p-100") {
  quote(input: { quantity: 2 }) {
    unitPrice
    quantity
    subtotal
  }
}

The custom Decimal scalar uses BigDecimal and serializes normalized monetary values as strings such as "99.90".

Field selection and over-fetching

A response carries exactly the fields the client selected. That guarantee describes the payload, not the work the server performed to produce it. Selection reaches a data source only where a resolver boundary exists.

query {
  catalog {
    id
    name
  }
}

No field here belongs to Pricing, so the Router never calls the Pricing subgraph. An E2E test stops Pricing and asserts that this query still succeeds. Inside a subgraph the same rule holds: fields backed by @BatchMapping and @SchemaMapping are skipped when unselected, while plain properties are read from objects the repository already returned whole.

@BatchMapping and N+1

Pricing resolves the price field with one bulk lookup for all catalog references in an execution. A counting-repository test proves that four items result in exactly one repository call.

The quote field takes an argument, which @BatchMapping does not support, so it batches through a named DataLoader registered on the BatchLoaderRegistry and returns a CompletableFuture. Its only data dependency is the item id; the quantity is applied afterwards as pure computation. A second counting test drives this through a real GraphQL execution, because a DataLoader only dispatches when the framework runs the query.

The two loaders are registered separately, so selecting both price and quote costs two bulk lookups — a constant, not one per item.

Incremental delivery with @defer

catalog {
  id
  name
  ... @defer(label: "commercial-data") {
    price
    priceLabel
  }
}

The Router sends core catalog data first and commercial data in labeled multipart patches. E2E tests parse the MIME boundary and verify the initial result, patch paths, labels, and completion marker.

Errors, composition, and the test pyramid

Stable error extensions include PRODUCT_NOT_FOUND, PRICE_NOT_FOUND, and VALIDATION_ERROR. Only Actuator health is exposed; Sandbox and GraphiQL are local tools.

JUnit 6 unit tests cover seeds, money, scalar coercion, labels, and batching. Spring integration tests load the real schemas. Router E2E tests cover federation, polymorphism, required fields, outage recovery, and deferred responses. Composition runs twice and is compared byte for byte to detect nondeterminism and stale artifacts.

Deliberate boundaries

This milestone does not include persistence, authentication, WebFlux, observability infrastructure, AWS/CDK, or production hardening. The in-memory repositories return whole objects, so no storage projection is derived from a selection set. Its focus is correct participation by synchronous Spring GraphQL services in an Apollo supergraph.
